# VisitSmoothie（医伴）项目说明：给接手的 AI

> 这份文档写给要接手这个项目的 AI 助手。读完你应该知道：我们要解决什么问题、产品怎么解决、每个功能做什么、代码在哪、有哪些不能碰的规矩、现在做到哪、还缺什么。
> 状态以 GitHub 仓库 `lucasnotfound59/TriMedManagement` 的 `main` 分支为准，截至 2026-10-04（main 提交 c1ca47c）。

---

## 1. 一句话

病人看病时说不清自己的情况，看完病又记不住医生的话，医生每次都得从头问。VisitSmoothie 是一个手机上的就诊助手：病人不舒服时跟它说，看完医生把医嘱拍给它，剩下的整理、记录、提醒都由它来做。

## 2. 要解决的问题

| 问题 | 具体表现 |
|---|---|
| 说不清 | 病人不知道怎么描述病情，用口语（比如「扭着疼」），觉得轻的症状就不说了 |
| 记不住 | 忘了什么时候开始的、以前得过什么、上次医生怎么说的、药怎么吃、哪天复诊 |
| 效率低 | 医生每次都要从头问一遍；病人回家后医嘱没人盯，下次复诊又从头说 |
| 太复杂 | 早期版本功能入口太多，老人看不懂该点哪里。所以现在的原则是：越简单越好，信息不减少 |

## 3. 解决思路

- **病人只做两件事**：不舒服时说一句（语音、打字、拍照都行）；看完医生拍医嘱或录音。
- **其余全部由系统完成**：追问、整理成医生看得懂的话、关联以前的记录、提取医嘱、生成待办和提醒、存档。
- **越用越好**：每次看病都存成一条就诊记录。下次再看病时，系统自动带上以前的经过，给医生的信息越来越完整。
- **AI 只整理和提醒，不诊断**：危险信号由写死的规则判断，不靠模型。

## 4. 用户

- 主要用户是普通患者，包括老人和慢病患者（高血压、糖尿病），也包括只会偶尔感冒发烧的年轻人。
- 演示时用的是一个虚构病人「林叔」（见第 9 节）。
- 所有病人数据都是虚构的。

## 5. 完整流程

1. **注册**：填七项资料，再设一个登录密码。也可以拍体检报告自动填。
2. **首页**：上半屏是「待办和提醒」，比如吃药、复诊；下半屏是「问一问」，有疑问随时问 AI。
3. **不舒服时，进「看病前」**：AI 先问「今天哪里不舒服？」，然后一次问一个问题，把缺的信息问清楚，最后生成一页给医生看的病情描述和就医建议。
4. **去医院**：把「给医生看」那一页打开或打印给医生。
5. **看完医生，进「看病后」**：拍病历、处方，或者经医生同意后录音。AI 整理出诊断、用药、注意事项、复诊时间，生成就诊计划（Clinical Plan），并把吃药和复诊放进首页提醒。之后问病人「还有没有不明白的」，病人勾选想了解的部分，AI 逐项解释，还可以接着追问。
6. **之后**：首页按时提醒；有疑问在「问一问」里问。
7. **下次不舒服**：回到「看病前」，系统自动带上以前的记录来问、来整理。

## 6. 界面结构（手机 App）

整个应用是一列手机宽度（最宽约 430 像素，电脑上居中显示）。

- **顶栏**：左边 logo，旁边写 VisitSmoothie；右上角一个小的红色「应急」按钮，每页都有。
- **底部切换栏，五格**：看病前（pre）、看病后（post）、中间凸起的圆形 logo 按钮（回首页，按钮下写 VisitSmoothie）、记录（report）、设置（set）。
- **首页**：上半屏「待办和提醒」，下半屏「问一问」。点进「问一问」，这一块会往上推开，变成全屏对话，左上角有「收起」。
- **中英文切换**：首页顶栏、设置页、未登录页面顶部都有「中 / EN」，选择会记住。

## 8. 产品规矩（不能改，除非人类明确同意）

1. **AI 不诊断**：只做整理、提示和初步分诊（要不要看医生、多急、挂哪科、去之前留意什么），不点名可能的疾病。
2. **用药边界**：不替人定剂量，不改医嘱，不评价医生的方案，不建议换药或改量。可以复述医生开的医嘱，也可以讲药品说明书上的一般用法，并说明以说明书和医生为准；剂量数字只复述医嘱。
3. **危险信号由写死的规则判断**，不交给模型。
4. **可信优先于文采**：给医生看的第一屏和时间线只按记录用规则生成；模型说的每一句都要过 `src/lib/ai/normalize.ts` 的过滤：不编病人没说过的话，不猜原因，不点名疾病，不建议做检查。
5. **不替用户编数字**：用户没说过的轻重、体温、用药，一律不写。
6. **用户自己记下的话保持原文**，切换语言时也不翻译。
7. **英文模式下 AI 暂时仍用中文回答**：英文的安全过滤做好并测试之前，不让 AI 说英文。界面上写着「AI replies are in Chinese for now」。
8. **中文模式下只能有中文**，例外只有品牌名 VisitSmoothie、药名和单位。
9. **所有病人都是虚构的**。
10. **想加约束，优先写成代码和测试**，不要只改提示词。

## 10. 设计规范

- **风格**：苹果「提醒事项」和「健康」App 的路子。浅灰底 `#F2F2F7`，白色分组卡片，细分隔线，系统字体，彩色小图标。
- **主色**：青瓷绿 `#007866`，取自 logo，白字对比度 5.4:1。2026-10-04 人类决定：全站不用蓝色。红色只留给应急和危险提示。
- **品牌**：logo 图片是 `public/visit-smoothie-logo.png`。凡是出现 logo 的地方，旁边都要写 VisitSmoothie。欢迎页和登录页用衬线大字。
- **硬规矩**：用户里有老人。正文至少 17 像素，要紧的话至少 20 像素，能点的地方至少 44 到 48 像素高，对比度至少 4.5:1，患者界面不出现技术词。
- **手机优先**：这一列里不要用 Tailwind 的 `sm:` `md:` `lg:`，它们按浏览器窗口宽度生效，电脑上会在窄列里误触发。底部固定的东西放在底栏之上（`bottom: var(--tab-bar)`）。弹窗从底部滑上来。
- **代码位置**：颜色、字号、材质在 `src/app/globals.css`；公共组件在 `src/components/ui.tsx`（Button、Card、IconTile、Toggle、Modal 等），新页面先用这些。规范文字版在 `docs/UI-STYLE.md`。
- **截图**：手机版截图在 `docs/手机版截图/` 和 `docs/手机版截图-英文/`。

## 11. 技术架构

- **框架**：Next.js 16（App Router，`src/` 目录）、React 19、TypeScript、Tailwind CSS 4。需要 Node.js 24 以上，服务端用了 `node:sqlite`。注意这个版本的 Next.js 和你训练数据里的可能不同，写代码前先看 `node_modules/next/dist/docs/`。
- **AI**：只在服务端的 `src/app/api/**` 里调用，Key 不进浏览器。
  - `AI_PROVIDER=glm` 用智谱：对话和整理 `glm-5`，认照片 `glm-4.6v`。
  - `AI_PROVIDER=claude` 用 Anthropic：对话、整理、认照片 `claude-opus-5-5`。
  - 语音转文字总是用智谱 `glm-asr-2512`。
  - 两家都没有 Key 或接口出错时，自动改用内置规则引擎 `src/lib/ai/fallback.ts`，演示不会挂，但不能认照片、不能听语音。
- **数据存储**：账号、档案、就诊记录加密存在服务端 `.data/visitsmoothie.sqlite`，用 AES-256-GCM 加密，每个账号互相隔开。密码用 scrypt 加盐哈希。登录连续错 5 次锁 60 秒。会话是 7 天的 httpOnly Cookie。加密主密钥 `DATA_ENCRYPTION_KEY` 第一次运行时自动生成，写进 `.env.local`，丢了数据就解不开。演示账号（林叔）只存在浏览器 localStorage。代码在 `src/lib/server/secure-db.ts`、`src/lib/store.tsx`、`src/app/api/auth/*`、`src/app/api/data`。
- **API 路由**：`auth`（注册、登录、退出、会话）、`data`（读写个人数据）、`chat`（问诊对话）、`summary`（病情描述）、`after`（医嘱整理）、`explain`（逐条解释）、`ask`（问一问）、`transcribe`（语音转文字）、`symptom-photo`（症状照片）、`checkup`（体检报告）、`annual`（年度摘要）、`health`（AI 连接测试）、`profile`。
- **独立模块**：`visit-smoothie/` 是队友做的独立账号原型（端口 4190，自己的数据库）；`patient-dictation/` 是可复用的语音转文字模块和命令行工具。
- **配置**：`.env.local`，变量见 `.env.example`。绝不能提交进仓库。
- **启动**：`npm install && npm run dev`，打开 http://localhost:3000 。macOS 上也可以双击根目录的「启动 VisitSmoothie.command」。

## 13. 仓库和协作规则

- **仓库**：github.com/lucasnotfound59/TriMedManagement，私有。`main` 是唯一的正式版本，所有人的成果都已经合进去了。
- **怎么开工**：每次都从最新的 main 开新分支：`git fetch origin && git switch -c 你的名字/功能名 origin/main`。不要在旧分支（yiban-patient、yiban-mobile、codex/* 等）上继续改。
- **推送前**：再 `git fetch origin`，把最新 main 合进来（rebase 或 merge）。有冲突时保留别人已有的功能，只加上你的改动，然后重新跑第 12 节的全部检查。
- **推送**：推自己的分支，再开 PR 或快进进 main。永远不要 force push，不要改写 main 的历史。
- **绝对不要**提交 `.env.local`、任何 API Key 或密码。之前仓库历史里泄露过一把智谱 Key，已要求吊销。
- **整合记录**：每次合进 main，在 `docs/MAIN-INTEGRATION.md` 末尾写一段：改了什么、怎么验证的。
- **团队习惯**：要快、要简单，按轮快速迭代。小活（翻译、改文字、改颜色、加几条数据）用小模型、快速做完；只有真正难的活才花大力气。
